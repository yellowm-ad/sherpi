## 1. 제품 개요

### 1-1. 한 줄 정의

**셰르피 앱은 산책 보조 로봇 셰르피의 눈과 리모컨이자, 어디로 걸을지 알려주는 안내자다.**

### 1-2. 슬로건

> **강아지를 자유롭게**

목줄을 쥔 손에서 보호자를 자유롭게, 좁은 반경에 묶인 반려견을 자유롭게. 로봇이 줄을 대신 잡고 보호자는 지켜보기만 합니다.

### 1-3. 왜 앱이 필요한가

로봇 단독으로는 **지금 어떤 상태인지 알 수 없습니다.** 로봇에 화면을 달면 비용·전력·방수가 전부 문제가 되고, 보호자는 어차피 스마트폰을 들고 있습니다. 로봇의 센서 데이터(장력·줄 길이·속도·안전등급)를 보여주고, 어디로 걸을지 정하고, 다녀온 기록을 남기는 레이어가 앱입니다.

동시에 앱은 **캡스톤 심사에서 "로봇 하나"가 아니라 "서비스"로 보이게 만드는 장치**이기도 합니다.

### 1-4. 타깃

| 구분 | 설명 |
|---|---|
| 1차 | 셰르피 로봇 보유자 — 로봇 제어·모니터링이 목적 |
| 2차 | 로봇 없는 반려인 — 코스 추천·기상 정보·커뮤니티만 이용 (로봇 기능은 잠금 표시) |
| 지역 | 1차 전주시 덕진구 (전북대 일대), 이후 전북권 확장 |

### 1-5. 차별점

| 기존 산책앱 (도그메이트·펫츠고 등) | 셰르피 |
|---|---|
| 사람이 걷는 걸 기록 | **로봇이 걷는 걸 제어·기록** |
| 날씨를 그대로 표시 | **반려견 기준 산책적합도 점수 + 지면온도 추정 경고** |
| 코스를 보기만 함 | **코스를 로봇에 전송해 자동 재주행** |
| — | **실시간 1인칭 영상 송출 (WebRTC)** |

### 2-4. ⚠️ PCA9685 채택에 따른 코드 변경

기존 `hal.py`의 `RealHAL`은 아두이노 나노에 시리얼로 보내는 구조였습니다.

```python
# AS-IS (아두이노 나노)
ser.write(f"S{steer:+.3f},T{speed:.3f}\n".encode())
```

PCA9685는 **파이가 I2C로 직접 PWM을 생성**합니다. 중간 MCU가 사라져 구조가 단순해지고, 하드웨어 타이머라 지터 문제도 없습니다.

```python
# TO-BE (PCA9685, I2C 0x40)
from adafruit_pca9685 import PCA9685
pca.frequency = 50                      # RC 표준 50Hz
# 12비트 4096스텝 / 주기 20,000μs → 1스텝 ≈ 4.88μs
# 1000~2000μs → 205~410 카운트
pca.channels[CH_STEER].duty_cycle = us_to_duty(steer_us)
pca.channels[CH_THROTTLE].duty_cycle = us_to_duty(throttle_us)
pca.channels[CH_GEAR].duty_cycle = us_to_duty(gear_us)
```

| 채널 | 용도 |
|---|---|
| CH0 | 조향 서보 (35kg) |
| CH1 | ESC 스로틀 |
| CH2 | 변속 서보 (2단 기어) |
| CH3~15 | 예비 |

**분해능 검증**: 4.88μs/스텝 → 조향 1000μs 범위를 205단계로 분할. 조향각 ±30° 기준 **0.29°/스텝**. 경로추종 제어에 충분합니다.

### 2-5. ⚠️ 릴 선택 관련 주의

구매하신 **RELUNE 릴루핀은 "트윈/더블 리드줄"**, 즉 개 2마리용입니다. 설계상 AS5600으로 릴 회전각을 읽어 줄 길이를 추정하는데, 두 가지를 확인해야 합니다.

1. **줄이 2가닥이면 릴 드럼도 2개**일 수 있습니다. 그러면 AS5600 자석을 어느 축에 붙일지, 두 줄의 길이를 따로 재야 하는지 문제가 생깁니다.
2. **"자동회전"이 꼬임방지 스위블**을 뜻한다면, 드럼과 함께 도는 축이 아니라 줄 끝이 따로 도는 구조라 자석 부착 위치가 달라집니다.

→ **실물 수령 후 분해해서 드럼 축 구조를 확인**하고, 1마리용 단일 드럼이 아니면 자석 부착 방식을 재설계해야 합니다. 플랫폼의 `leash_len_m` 필드는 이 결과에 따라 단일값/배열이 결정됩니다.

## 4. 페르소나 & 핵심 시나리오

### 4-1. 페르소나

**지훈 (28, 직장인, 포메라니안 "콩이" 4kg)**
퇴근이 늦어 산책을 자주 거른다. 로봇이 대신 걸어주길 바라지만, 눈앞에서 안 보이면 불안하다.

### 4-2. 핵심 시나리오 — "첫 자동 산책"

```
1. 앱 실행 → 홈에서 오늘 산책적합도 82점 확인
   "지면온도 추정 31℃ · 미세먼지 보통 · 산책 좋음"

2. [지도] 탭 → 저장해둔 "덕진공원 기본 산책로" 코스 선택
   → "셰르피에 전송" 버튼

3. 로봇에 콩이 리드줄 연결 → 앱에서 [티칭 시작]
   → 지훈이 송신기로 한 번 몰아 경로를 기억시킴
   → 앱 상단에 "키프레임 47개 기록 중" 실시간 표시

4. [자동주행 시작] → 로봇이 기억한 경로를 재주행
   → 앱 로봇 탭에서 실시간 확인:
      장력 8.2N (정상) · 줄 길이 2.4m · 속도 0.9m/s · 매칭 신뢰도 0.81

5. 콩이가 갑자기 당김 → 장력 34N 급상승
   → 로봇이 자동 감속 → 앱에 "L2 경고: 견인 과다, 감속 중" 배너

6. 지훈이 [카메라] 탭 → 0.3초 지연 1인칭 영상으로 상황 확인
   → 문제없음 확인 후 계속

7. 산책 종료 → 자동 리포트
   "1.8km · 32분 · 평균 0.94m/s · 최대장력 34N · 경고 1회"
```

## 6. 기능 요구사항

### F-1. 셰르피 실시간 대시보드 ★P0

**화면**: S10

#### 표시 항목

| 항목 | 출처 | 표현 |
|---|---|---|
| 연결 상태 | `last_seen_at` | 온라인(3초 이내) / 지연 / 오프라인 |
| **장력** | SBA-50L + HX711 | 게이지 0~50N, 임계선 표시 (8 / 30 / 40N) |
| **줄 길이** | AS5600 회전각 | 0~5m 바, L_SOFT 3.0 / L_HARD 4.5 / L_MAX 5.0 |
| 주행 속도 | 스로틀 지령 + 추정 | m/s |
| 조향 | 조향 지령 | −1(좌) ~ +1(우) 인디케이터 |
| **안전등급** | `safety.py` L0~L3 | 색상 배지 (초록/노랑/주황/빨강) |
| 고장 코드 | F1~F6 | 발생 시 배너 + 설명 |
| 주행 모드 | idle / teach / follow / estop | 칩 |
| 경로 진행도 | `kf_index / kf_total` | 진행바 |
| 매칭 신뢰도 | ORB 매칭 품질 | 0~1, 0.5 미만 시 경고 |
| 배터리 | 전압 → % (P2) | §7-6 참조 |

#### 수용 기준

- [ ] 로봇이 1Hz로 보낸 데이터가 **2초 이내** 화면에 반영된다
- [ ] 3초 이상 수신이 없으면 "연결 끊김"으로 전환하고 마지막 수신 시각을 표시한다
- [ ] 안전등급이 L2 이상으로 바뀌면 상단에 배너가 뜨고 진동(Vibration API)이 울린다
- [ ] 오프라인 상태에서는 제어 버튼이 전부 비활성화된다

### F-2. 셰르피 원격 제어 ★P0

#### 명령 목록

| 명령 | 설명 | 안전등급 |
|---|---|---|
| `ESTOP` | 즉시 정지 (스로틀 중립) | 긴급 |
| `START_TEACH` | 경로 티칭 시작 | 일반 |
| `STOP_TEACH` | 티칭 종료 + 경로 저장 | 일반 |
| `START_FOLLOW` | 저장 경로 자동주행 시작 | **확인 필요** |
| `PAUSE` / `RESUME` | 일시정지 / 재개 | 일반 |
| `SET_ROUTE` | 주행할 경로 지정 | 일반 |
| `SET_SPEED_LIMIT` | 최대속도 제한 (0.5~1.5 m/s) | 일반 |

#### ⚠️ 안전 정책 — 반드시 지킬 것

> **원격 정지는 보조 수단입니다. 1차 안전장치는 로봇의 물리 E-stop 버튼입니다.**
>
> 명령은 네트워크를 경유하므로 **약 1초의 지연과 단절 가능성**이 있습니다. 네트워크에 의존하는 정지를 안전설계의 주 수단으로 삼으면 안 됩니다. 앱에도 이 문구를 명시합니다.

- `START_FOLLOW`는 **모달 확인**을 거친다 ("주변에 사람·차량이 없는지 확인하셨나요?")
- 로봇은 서버 명령을 **3초 이상 못 받으면 스스로 감속·정지**한다 (워치독, 로봇 측 구현)
- 앱의 ESTOP 버튼은 **화면 어디서든 접근 가능한 플로팅 버튼**으로 둔다

#### 수용 기준

- [ ] ESTOP 발신 후 로봇 ack까지 **2초 이내**, 실패 시 "물리 버튼을 사용하세요" 경고
- [ ] 명령은 `pending → sent → acked | expired` 상태를 가지며 앱에 표시된다
- [ ] 10초간 ack가 없으면 `expired` 처리하고 재시도를 제안한다

### F-3. 실시간 카메라 송출 (WebRTC) ★P0

**화면**: S11

#### 구성

```
[Pi 카메라] → libcamera → [MediaMTX] ─ WebRTC(WHEP) ─→ [Cloudflare Tunnel] ─→ [앱 브라우저]
                                                          (고정 HTTPS 주소)
```

- MediaMTX는 라즈베리파이 카메라를 **공식 지원**합니다 ([문서](https://mediamtx.org/docs/publish/raspberry-pi-cameras))
- 영상은 **서버(Vercel)를 경유하지 않고** 로봇 ↔ 브라우저 P2P로 흐릅니다. Vercel 대역폭 비용이 0입니다
- Cloudflare Tunnel로 고정 HTTPS 주소를 얻어 공유기 포트포워딩 없이 접속합니다

#### 요구사항

| 항목 | 목표 |
|---|---|
| 지연 | **0.5초 이하** |
| 해상도 | 640×480 @ 15fps (기본) / 1280×720 @ 30fps (와이파이 환경) |
| 음성 | 미포함 (대역폭 절약) |
| 화면 | 전체화면 + 오버레이 (장력·속도·안전등급 HUD) + ESTOP 버튼 |

#### 수용 기준

- [ ] LTE 테더링 환경에서 지연 1초 이하로 재생된다
- [ ] 연결 실패 시 "영상 연결 실패" 플레이스홀더와 재시도 버튼을 표시한다
- [ ] 영상 화면에서도 ESTOP 버튼이 항상 보인다
- [ ] 백그라운드 전환 시 스트림을 끊어 데이터·배터리를 아낀다

> **⚠️ 전제**: 라즈베리파이 **카메라 모듈이 BOM에 없습니다**(§2-3). 이 기능은 카메라 확보가 선행되어야 하며, 경로 기억 주행도 같은 카메라를 씁니다.

### F-4. 산책코스 DIY + 로봇 전송 ★P1

**화면**: S07, S08, S09

#### 코스 만들기

1. 카카오맵에서 **경유점을 탭으로 찍어** 경로를 그린다
2. POI 추가: `급수대` `배변봉투함` `그늘` `주의구간` `펫프렌들리`
3. 자동 계산: 총 거리, 예상 소요시간(1.0 m/s 기준), 난이도(경사·거리)
4. 공개/비공개 설정 후 저장

#### 로봇 전송 — 중요한 한계

> **그린 경로가 곧바로 자율주행 경로가 되지는 않습니다.**
>
> 셰르피의 자율주행은 **카메라로 본 장면(키프레임)을 기억해 되짚는 방식(Visual Teach & Repeat)** 입니다. 지도에 그린 GPS 좌표열만으로는 주행할 수 없습니다.
>
> 따라서 앱의 코스는 **① 티칭 가이드** (사람이 몰 때 "이 경로대로 가세요" 안내) 와 **② 기록 메타데이터** (티칭된 키프레임 경로에 지도 코스를 매칭) 역할을 합니다.

```
[앱에서 코스 선택] → [셰르피에 전송] → 로봇이 route_id 수신
        ↓
[티칭 모드] 사람이 송신기로 그 경로를 한 번 주행
        ↓
로봇이 키프레임 생성 (신뢰도 < 0.5 기준, 약 0.5m 간격)
        ↓
[자동주행] 기억한 키프레임을 되짚어 재주행
        ↓
주행 궤적이 앱 지도에 기록으로 표시됨
```

#### 수용 기준

- [ ] 경유점 2개 이상이면 저장 가능하다
- [ ] 거리·소요시간이 자동 계산된다
- [ ] 코스 전송 후 로봇 대시보드에 해당 코스명이 표시된다
- [ ] 티칭 완료 시 키프레임 수와 실제 주행 거리가 코스에 기록된다

### F-5. 기상·환경 정보 + 산책적합도 점수 ★P1

**화면**: S06 (홈 상단 카드)

이 기능이 **"그냥 날씨앱"과 셰르피를 가르는 지점**입니다. 사람 기준이 아니라 **반려견 기준**으로 환산합니다.

#### 데이터 출처

| 항목 | API | 비용 |
|---|---|---|
| 기온·습도·풍속·강수확률·하늘상태 | [기상청 단기예보 조회서비스](https://www.data.go.kr/data/15084084/openapi.do) | 무료 |
| 자외선지수 | 기상청 생활기상지수 | 무료 |

#### 산책적합도 (Walk Score) 산출

```
WalkScore = 100 − (지면온도 감점 + 체감온도 감점 + 대기질 감점 + 강수 감점 + 자외선 감점)
```

**① 지면온도 추정** — 가장 중요한 지표

아스팔트·보도블록은 기온보다 훨씬 뜨거워져 **발바닥 화상**을 유발합니다.

```
T_surface ≈ T_air + k × (1 − 운량/10) × 주간계수
  k = 25℃ (직사광 기준)
  주간계수 = 10~16시 1.0, 그 외 선형 감소, 일몰 후 0
```

| 추정 지면온도 | 판정 | 감점 |
|---|---|---|
| < 40℃ | 안전 | 0 |
| 40~51℃ | 주의 — 짧게, 그늘 위주 | 20 |
| **≥ 52℃** | **위험 — 화상 가능, 산책 금지 권고** | 60 |

> 52℃ 기준은 "손등을 7초간 대고 있을 수 없으면 산책 금지"라는 통용 규칙에 대응합니다. **단, 추정식의 계수 k=25℃는 일반적으로 인용되는 값이며 전주 지역 실측으로 보정이 필요합니다 (§14 확인 필요).**

**② 체감온도**: 여름 열지수(기온+습도), 겨울 풍속냉각
**③ 대기질**: ~~PM2.5~~ — 2026-10-19 범위에서 제외
**④ 강수확률** ≥60% 시 30점 감점
**⑤ 자외선지수** ≥8 시 15점 감점

#### 표시

```
┌─────────────────────────────┐
│  오늘의 산책      🟢 82점    │
│  ───────────────────────    │
│  산책하기 좋아요             │
│                             │
│  🌡 기온 18℃ (체감 16℃)     │
│  🔥 지면 추정 31℃  안전      │
│  😷 PM2.5 12 좋음            │
│  ☔ 강수확률 10%             │
│                             │
│  💡 오후 3시 이후가 가장 좋아요│
└─────────────────────────────┘
```

#### 수용 기준

- [ ] 현재 위치 기준 격자(nx, ny)로 변환해 기상청 API를 호출한다
- [ ] 응답은 **30분 캐시**한다 (API 일일 호출 한도 보호)
- [ ] 지면온도 추정값이 52℃ 이상이면 홈 상단에 빨간 경고 배너를 고정한다
- [ ] API 실패 시 마지막 캐시값과 "갱신 실패" 표시를 보여주고 앱은 계속 동작한다

## 7. 로봇 ↔ 플랫폼 연동 아키텍처

### 7-1. 전체 구조

```
┌──────────────────────┐
│  셰르피 로봇 (Pi)      │
│  ┌────────────────┐  │      ① 텔레메트리 업링크 (1Hz)
│  │ walkbot        │  │      HTTP POST /api/robots/:id/telemetry
│  │ bridge/        │──┼──────────────────────────────┐
│  └────────────────┘  │                              │
│  ┌────────────────┐  │      ② 명령 폴링 (1Hz)        │
│  │ MediaMTX       │  │      HTTP GET /api/.../pending│
│  └───────┬────────┘  │◄─────────────────────────────┤
└──────────┼───────────┘                              │
           │                                    ┌─────▼──────┐
           │ ③ WebRTC (P2P, 서버 미경유)         │  Vercel    │
           │                                    │  Next.js   │
           ▼                                    │  API Routes│
  ┌─────────────────┐    ④ SSE (서버→앱)        └─────┬──────┘
  │ Cloudflare      │                                 │
  │ Tunnel          │                           ┌─────▼──────┐
  └────────┬────────┘                           │  Neon      │
           │                                    │  Postgres  │
           ▼                                    └────────────┘
    ┌──────────────┐                                  ▲
    │  보호자 폰    │──────────────────────────────────┘
    │  (모바일 웹)  │         ⑤ 명령 발신 POST
    └──────────────┘
```

### 7-2. 왜 이 구조인가

| 선택 | 이유 |
|---|---|
| 로봇 → 서버는 **HTTP POST** (WebSocket 아님) | 로봇이 지속 연결을 유지할 필요가 없음. 네트워크가 끊겼다 붙어도 다음 POST부터 자동 복구 |
| 서버 → 앱은 **SSE** | Vercel Functions가 SSE를 지원하며, 서버→클라이언트 단방향이라 우리 용도에 정확히 맞음. `EventSource`가 끊기면 자동 재연결 |
| 명령은 **로봇이 폴링** | 로봇에 인바운드 포트를 열 필요가 없음 (LTE·핫스팟 환경에서 필수) |
| 영상은 **P2P WebRTC** | 서버를 안 거쳐 지연이 낮고 Vercel 대역폭 비용이 0 |

> **⚠️ Vercel 함수 실행시간 제한**: Hobby 플랜은 함수 최대 300초입니다. SSE 스트림도 이 제한을 받으므로 **클라이언트에 재연결 로직이 필수**입니다. `EventSource`는 기본적으로 자동 재연결하지만, `Last-Event-ID`로 유실 구간을 이어받도록 구현합니다. SSE가 불안정하면 **2초 폴링으로 폴백**합니다.

### 7-3. 텔레메트리 페이로드

```json
{
  "ts": "2026-10-19T12:34:56.000Z",
  "mode": "follow",
  "safety_level": 1,
  "faults": [],
  "tension_n": 12.3,
  "leash_len_m": 2.45,
  "speed_cmd": 0.42,
  "steer_cmd": -0.15,
  "lat": 35.8465, "lng": 127.1295, "gps_src": "phone",
  "route_id": 12,
  "kf_index": 34, "kf_total": 120,
  "match_quality": 0.78,
  "battery_v": null
}
```

- 전송 주기 **1Hz**, 실패 시 최대 30개까지 로컬 버퍼링 후 재전송
- 인증: 로봇별 발급 API 키를 `Authorization: Bearer <robot_api_key>` 헤더에 실음

### 7-4. 명령 큐

```
앱 POST /api/robots/:id/commands  →  robot_commands (status=pending)
로봇 GET  /api/robots/:id/commands/pending  (1Hz)  →  status=sent
로봇 POST /api/robots/:id/commands/:cid/ack        →  status=acked
10초 경과 미응답                                    →  status=expired
```

ESTOP은 큐를 건너뛰고 **최우선 반환**하며, 로봇은 수신 즉시 다른 처리를 중단하고 스로틀을 중립으로 보냅니다.

### 7-5. GPS — 보호자 폰으로 대체

BOM에 GPS 모듈이 없습니다. **보호자 스마트폰의 `navigator.geolocation`을 로봇 위치로 사용**합니다.

- 보호자는 로봇 바로 옆에 있으므로 오차가 수 미터 수준이고, 지도 표시 용도로는 충분합니다
- 추가 비용 0, 배선 0
- 한계: 보호자가 멀어지면 부정확해집니다. 앱이 `gps_src: "phone"`을 표시해 사용자가 알 수 있게 합니다
- 로봇에 GPS 모듈을 다는 경우 `gps_src: "robot"`으로 바뀌며 플랫폼 코드는 그대로입니다

### 7-6. 배터리 잔량 — P2로 유예

파이에는 ADC가 없어 3S LiPo 전압을 직접 못 읽습니다. ADS1115 + 분압저항이 필요한데 BOM에 없습니다.

- **P1**: 배터리 칸을 `측정 없음`으로 표시하고, ESC의 저전압 보호(LVC)에 맡깁니다
- **P2**: ADC 추가 시 전압→% 매핑 (12.6V=100%, 11.1V=50%, 9.9V=0%)

### 11-4. 인구 밀집도를 명목상으로 두는 이유

조사 결과 전북권에 바로 쓸 수 있는 무료 실시간 유동인구 API가 없습니다.

- 서울시 `생활인구` 데이터는 **서울 전용**
- 통신사(SKT·KT) 유동인구 API는 **유료 B2B 계약**
- 한국관광공사 TourAPI 혼잡도는 **관광지 한정**

→ 1차에서는 mock, 발표에서는 "상용화 시 통신사 API 연동" 으로 설명합니다.
→ **대안 아이디어**: 자체 사용자의 산책 기록이 쌓이면 **"이 시간대에 이 코스를 N명이 걸었어요"** 라는 자체 혼잡도를 낼 수 있습니다. 데이터가 모이기 전까지는 성립하지 않지만, 향후계획 슬라이드에 넣기 좋은 논리입니다.

## 17. 미확인 / 리스크 (솔직하게)

- **지면온도 추정식의 계수 k=25℃는 일반적으로 인용되는 값이며, 제가 1차 문헌으로 검증하지 못했습니다.** 발표에서 수치를 단정하지 말고 "추정치, 실측 보정 예정"으로 표기하세요.
- **라즈베리파이 본체가 BOM에 없습니다.** 기존 보유분이라면 모델(3B+/4/5)에 따라 WebRTC 인코딩 성능이 크게 다릅니다. Pi 4 이상을 권하며, Pi Zero 2 W는 ORB 특징점 매칭과 영상 인코딩을 동시에 감당하기 어렵습니다.
- **ORB 매칭 + H.264 인코딩 + 센서 폴링을 동시에 돌릴 때의 CPU 부하를 측정하지 못했습니다.** 영상 송출 때문에 경로추종 루프가 느려지면 주행 품질이 떨어집니다. M3에서 반드시 부하 테스트를 하고, 필요하면 영상 해상도를 낮추거나 하드웨어 인코더(Pi 4의 H.264 HW 인코딩)를 쓰세요.
- **지면온도 추정식이 계절을 반영하지 못합니다.** 같은 "맑은 낮"이라도 6월과 11월의 일사량이 다른데 똑같이 k=25를 적용하므로, 선선한 계절에는 지면온도를 과대평가합니다(18℃ 봄 오후에 41℃로 추정). 실측 후 k를 월별 또는 태양고도 함수로 바꿔야 합니다.
- **Walk Score 가중치는 제가 설계한 것이며 검증된 기준이 아닙니다.** 수의학적 근거가 있는 건 "지면 52℃ 화상 위험"과 "PM2.5 한국 환경기준"뿐이고, 나머지 감점 배분은 임의입니다. 발표에서 "자체 설계 지표"로 정직하게 밝히세요.
- **로봇 조립이 끝나기 전에는 실제 연동을 검증할 수 없습니다.** `scripts/mock-robot.ts`로 앱을 먼저 완성하는 것이 유일한 리스크 회피책입니다.
- 마켓·인구밀집도는 **명목상 구현**이라는 사용자 결정을 그대로 반영했습니다. 심사에서 "이건 동작하나요?" 질문이 나올 수 있으니 미리 답변을 준비하세요.
